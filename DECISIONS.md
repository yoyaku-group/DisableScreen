# DECISIONS — DisableScreen → RunClosed

Décisions d'architecture. Un ADR = une décision. Nom RunClosed **provisoire** (package Swift + binaire CLI `runclosed` uniquement ; repo/bundle id inchangés jusqu'à G5).

| ADR | Décision | Raison / compromis |

| 002 | Noyau Swift (`RunClosedCore`) indépendant d'AppKit et des API macOS via protocoles injectables. | Tests déterministes (horloge, backends fakes) sans matériel. |

## Décisions de périmètre (cette tranche G0–G2)

- Même repo, branche de mission `agent/claude/20260911/…` (worktree lié via `yy mission`). Register forcé (`--force-capacity`) : `--headless` n'exécute aucun harness, coût CPU nul ; charge due aux sessions voisines.
- Tests matériels (capot, écran externe MB16AH) derrière `RUNCLOSED_HW_OPTIN=1`, exécution seulement avec Ben présent. Un seul écran (XDR intégré) branché → externe = `BLOCKED_HARDWARE`.
- Aucun backend capot privé (`coke`) exploré ici (décision post-qualification).

| 019 | **G2d — la surface quotidienne est le popup à toggles dans l'app Swift ; l'app Python `DisableScreen` est retirée (backup réversible). Le capot mute par `sudo -n pmset` (règle sudoers M6 existante, readback autoritaire + retry borné) ; la luminosité externe reste `softwareDim` overlay, la builtin passe par CoreDisplay dlopen depuis `/System/Library/Frameworks/`. Le parsing `pmset -g` est whitespace-run (les TABULATIONS réelles ne matchaient pas l'espace littéral — cause racine du « ça ne marche pas » : le readback mentait `false` sur un flag réellement muté).** | G2d (2026-09-20) : parité complète avec le panneau Python (toggles, luminosité, résolution, login item) sur le moteur Swift testé (G2b/G2c). Le défaut de parsing est la leçon centrale : un readback faux transforme un succès en échec rapporté — l'invariant ADR 009 (l'observation décide) n'est tenu que si le parseur d'observation est correct ; d'où parseur pur + tests de régression + retry borné pour la latence de propagation du flag noyau. |
| 020 | **Le `doctor` rapporte des faits distincts : la qualification du chemin capot de l'app (`sudo -n /usr/bin/pmset`, qualifié live 2026-09-20) et le statut du wrapper CLI `run --lid` (non implémenté, exit 3, ADR 007) sont deux champs séparés — plus aucune chaîne globale « unqualified ».** | G5 (2026-09-20) : `lid.backend="unqualified"` était vrai en G2 (aucun moteur capot) mais périmé depuis G2c/G2d + la qualification live (matrice compatibilité PASS). | 021 | **B2 (« ne jamais remettre OFF ce qu'on n'a pas posé ») protège les chemins AUTOMATIQUES (restore au quit, scripts, agents) — jamais une commande explicite de l'opérateur.** `LidMutationService.setEnabled(_:initiator:)` : `.automatic` (défaut) garde le refus `notOwned` ; `.operatorCommand` (switch du popup, CLI `lid-stay-awake off --operator`) saute le gate d'ownership. B1 (UNKNOWN ≠ OFF) reste bloquant dans les deux cas, et seul un OFF **vérifié par readback** remplace un record stale (ADR 015 intact : aucune auto-mutation, purge seulement après observation). Un refus du toggle est affiché sous le libellé, plus jamais un retour silencieux du switch. | Incident 2026-09-29 (Ben) : flag posé le 25/09 13:03 (boot A), reboot à 17:33, `disablesleep` **resté à 1** après reboot → record stale `recoveryPending` → chaque clic OFF refusé `notOwned` et le switch revenait au bleu, sans message. Le port Swift était plus strict que l'app Python (manuel OFF toujours permis, seul B1 bloquait) : il confondait l'invariant du restore automatique avec la volonté de l'opérateur, qui est l'autorité sur ce flag global. La résolution « par l'opérateur » qu'ADR 015 prévoyait n'avait aucun chemin UI. 4 tests de régression. |
| 022 | **Garde batterie faible : le flag `disablesleep` est relâché et le Mac mis en veille quand la batterie devient critique sur batterie — par le chemin `.automatic` existant (B1 + B2 inchangés), jamais sur secteur.** Politique pure `LowBatteryPolicy` (Core) : alerte à **20 %**, `releaseAndSleep` à **10 %** ou à **≤ 10 min** d'autonomie *dans la bande des 20 %* (une estimation bruitée juste après débranchement ne met jamais en veille un Mac à 80 %) ; secteur ou source inconnue ⇒ aucune action ; flag OFF ⇒ rien à protéger (macOS garde sa veille de secours). Exécution `LowBatteryGuardService` (MacSystem) : `LidMutationService.setEnabled(false, .automatic)` → readback vérifié → verrou `releasedByGuard` (écrit depuis le résultat, B3) → `/usr/bin/pmset sleepnow` ; échec backend alors qu'on possède le flag ⇒ veille tentée quand même (best effort, non persistant). **Hystérésis** : le flag relâché n'est réarmé (`setEnabled(true, .automatic)`) que sur secteur **et** charge > 15 % ; une commande explicite de l'opérateur (switch du popup, CLI `lid-stay-awake on|off`) annule le réarmement dû ; un flag observé ON efface la dette (ADR 009). Anti-flap : alertes une fois par épisode, réinitialisées seulement sur secteur au-dessus de 20 % ; après relâchement le flag lit OFF ⇒ aucun `sleepnow` répété au réveil. **Propriété d'urgence (DÉCIDÉE 2026-10-15, décideur : orchestrateur en application de l'instruction de Ben « veille de secours à 10 % »)** : dans la seule branche `releaseAndSleep` (sur batterie ET charge ≤ 10 % ou ≤ 10 min dans la bande des 20 %), si le flag est observé ON et que **le record `owned_lid.json` de RunClosed existe mais vient d'un boot précédent** (`staleRecord`), il est traité comme propriété d'urgence : raison `emergencyStaleOwnership`, initiateur `LidMutationService.Initiator.lowBatteryEmergency` (le service re-vérifie lui-même que le record est le nôtre), relâchement puis `pmset sleepnow`, notification critique dédiée, **ligne d'audit persistée** (`low_battery_audit.jsonl`, écrite avant la veille). Raison : relâcher est le sens protecteur, l'alternative est la coupure sèche du 2026-10-14. B2 reste intact partout ailleurs (toggles normaux, chemin d'alerte, secteur, restore-on-quit, `.automatic`). **Aucun record RunClosed (flag posé par un autre outil) ⇒ alerte seule, jamais muté (`criticalNotOwned`).** Relevé `BatteryReadback` : IOKit public `IOPSCopyPowerSourcesInfo`/`IOPSGetPowerSourceDescription`, tri-état (inconnu jamais converti en « secteur »). Verrou persistant `low_battery_guard.json` (`RunClosedPersistence`, atomique, corrompu ⇒ défaut = aucun réarmement). Minuterie 30 s (file série, jamais en parallèle d'un toggle) dans l'app ; coupe-circuit `defaults write com.benjaminbelaga.RunClosed lowBatteryGuardEnabled -bool false`. CLI lecture seule : `runclosed low-battery status` / `simulate`. État réel reproduit le 2026-10-15 : record du boot 8C8825C7, boot courant A6CB8DFE, `recoveryPending: true` ; le relâchement opérateur (`lid-stay-awake off --operator`) a fonctionné (SleepDisabled 0 vérifié) ; la batterie est descendue à 9 % **sur secteur** (100 W, InstantAmperage jusqu'à ≈ -1180 mA). `runclosed low-battery status` expose `lidRecord.recoveryPending`, `protection` et le remède en un clic. | Incident 2026-10-14 21:58 : sur batterie avec ~50 agents, le Mac est passé de 41 % à 1 % et s'est coupé net ; `pmset -g` montrait `SleepDisabled 1` posé par RunClosed, donc aucune veille de secours alors que `hibernatemode 3` aurait figé tous les processus sur disque. Seuils décidés par Ben (2026-10-15). Le cas « secteur insuffisant mais branché » (batterie qui se vide sur AC) relève de la sonde Guardian `ac-draining`, pas de cette garde. 57 tests (27 politique + 12 relevé + 13 service + 5 persistance/verrou). | 023 | **Session de maintien éveillé minutée : le flag `disablesleep` reçoit une échéance visible, et c'est le MÊME tick que la garde batterie qui l'applique.** `KeepAwakeSession { id, startedAt, endsAtWall, endsAtContinuous, bootID, pausedReason, schemaVersion }` (Core) ; `endsAt` nul = session indéfinie, c'est-à-dire l'interrupteur simple d'aujourd'hui, inchangé. Politique pure `SessionPolicy` : dû si `mach_continuous_time` dépasse `endsAtContinuous` **sur le même boot** (cette horloge continue de compter pendant la veille), OU si l'horloge murale dépasse `endsAtWall` (seule source valable après un reboot, le compteur repartant de zéro) ; refus de démarrer une session minutée quand le flag est observé ON mais non possédé (l'expiration échouerait silencieusement en `notOwned`) ; prolonger (+30 min, depuis MAINTENANT) et terminer. Nouvelle abstraction `ContinuousClock` (`mach_continuous_time` converti par `mach_timebase_info`) — **pas** `LeaseEngine`, dont l'horloge `systemUptime` s'arrête pendant la veille (`Clock.swift:14-17`), ce qui est exactement la fenêtre d'usage de cette fonctionnalité. Persistance `SessionStore` (`session.json`, même discipline qu'`OwnedLidAssertion` : init canonique + URL pour les tests, `schemaVersion`, écriture `.atomic`, fichier corrompu = aucune session). Journalisation AVANT effet : le record est écrit avant le flag ; si le flag échoue, le record est supprimé.
